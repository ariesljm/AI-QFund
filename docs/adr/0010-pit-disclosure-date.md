# PIT 公告日口径（Point-in-Time via Disclosure Date）

架构决策：所有用到"某决策日可见的季报持仓"的读路径，都只能看到 **`disclosure_date <= d`** 的报告期；拿不到公告日时退化为 **报告期 + 15 个工作日** 的保守估计（宁晚不早）。

## 决策

- `fund_holdings` 增列 `disclosure_date`（迁移幂等回填存量，不落 NULL）。
- 读取闸门：`get_holdings(code, as_of=d)` / `get_holdings_summaries(codes, as_of=d)` 只取 `disclosure_date <= d` 的报告期；不传 `as_of` 的实时路径取库内最新（公告日过滤由调用方按需开启）。
- 公告日来源：东财 `jjcc` 页面**实测不含**公告日期（只有报告期标签）→ 一律走保守推算：`报告期 + 15 个工作日`（`trading_calendar.disclosure_date`，全历史交易日历 `trade_dates_history` 缓存；日历覆盖不到时退化 +31 自然日上界）。
- **不打标记列**（"是否估算"的 flag）：一律是估算值，加标记列永远为 1，是无用死重。

## 为什么是它

1.x 及 `quant-overhaul-plan.md` §3 曾写 `report_date <= d`（报告期口径）——**明确否决**：40 日窗口下有 55% 的样本会被"报告期末已公告"的错觉污染（最新一期季报在决策日尚未披露，却把它的持仓当成已知）。

## Considered Options

- **报告期口径 `report_date <= d`** — 被拒（见上，泄漏污染）。
- **抓真实公告日** — 被拒：东财无私域公告日，逐基金解析公告文本量级与维护成本不可行。
- **纯 +31 自然日退化** — 采纳其安全方向但升级：工作日口径更贴合披露期限法理（法定披露期限以工作日计），+31 仅作日历缺失时的上界。

## Consequences

- 回测/训练/素材装配的"决策日可见持仓"一律过本闸门；实时推荐路径不传 `as_of` 时维持"库内最新"（当天必然可见）。
- 季报披露高峰（4 月底/8 月底）附近，可见期次会比"报告期"口径晚约 1~3 周——这是**正确**的谨慎，样本量的代价换 PIT 的真实性。

## 冲突标注

与 `docs/quant-overhaul-plan.md` §3 的 `report_date <= d` 冲突，**以本 ADR 为准**（共识 Q15 已拍板）；与 ADR-0005（数据读收敛）一致：读数闸门收敛在 repo 层，非各调用方自行拼接。
