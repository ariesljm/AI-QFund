# 跟踪对象抽象（Tracked Object Abstraction）

架构决策：三级状态机（HOLD/WATCH/EXIT，票 15）作用于**跟踪对象**，默认实现为推荐记录；为将来接入用户真实持仓留一个**可选关联实体**的缝——加实体是加表，不是改状态机。

## 决策

- 状态转移是纯函数：`transition(current, signals)` 不读库、不读全局（`app/engine/state_machine.py`），同一套转移逻辑适用任何跟踪对象。
- 跟踪对象携带 `object_type / object_id` 两个**挂载字段**：`object_type="recommendation"`（默认）或未来 `"user_position"`。状态机本身不感知对象类型——对象身份只是把状态记录锚定到哪个实体上。
- **缝是 schema 级**：`object_type` 建表即存在，接入用户持仓只需插入新行，不触碰转移逻辑与阈值。

## 为什么是它

1.x 的 R2/R3/R4 防线全部围绕"赛道"定义（赛道下线即防线作废）；新状态机若继续把状态挂在推荐记录上却不留口子，未来接入用户持仓就要改状态机本身。Q16 共识要求"加表而非改状态机"。

## Considered Options

- **状态机直接绑定推荐记录（无抽象）** — 被拒：用户持仓接入时转移逻辑被迫复制一份或加分支。
- **完整对象模型（ORM/基类）** — 被拒（YAGNI）：当前唯一消费者是推荐记录，抽象到"两个挂载字段"即满足缝的要求，不做类继承体系。

## Consequences

- `monitor_events`（或 2.0 的等价状态表）增加对象身份字段即可复用全部转移逻辑。
- 阈值/标定策略（票 15"进配置"）与对象类型无关，配置化在接线层完成。
- 本 ADR 不预判用户持仓的**数据流**（持仓从哪来、多久同步）——那只在真正接入时才有意义。

## 冲突标注

与 ADR-0006（决策读缝）正交：读缝管数据访问，本 ADR 管状态归属。与 1.x 的《监控状态机》无继承关系——那是"推荐 × 赛道"二维体系，已随赛道下线。
